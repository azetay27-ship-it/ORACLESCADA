# דף בדיקה בשטח — NILIT / Vuniq / RS232

הוכן ב־27.09.2026. מטרת הביקור: לתעד מערכת עובדת, לזהות את התוכנה ואת החיבור הפעילים, לאמת שהנתונים מתעדכנים ולהביא חומר שיאפשר בדיקה ופיתוח ללא מחשב המפעל. נניח לצורך התכנון שהקישור שנמסר הוא RS232 עם 3964R; זה עדיין אינו מזהה את התוכנה המשדרת או את תוכן ההודעות.

בדיקות הביקור הן צפייה ואיסוף. אין צורך בגישה לכל תוואי הכבל. אין להסיק משני קצוות נראים שאין מתאם או רכיב ביניים בתוואי שלא נבדק.

## 1. צילום שני הקצוות וזיהוי התוכנה

- [ ] תמונה של מחשב Vuniq ושל מחשב ה־HMI, כולל מדבקות יצרן ודגם.
- [ ] תמונה של כל מחבר נגיש ושל כל מתאם גלוי, וסימון איזה קו/אקסטרודר הוא משרת. לא מנתקים כדי לצלם.
- [ ] ב־HMI, אם מערכת ההפעלה ותפריט About נגישים בלי לצאת מהתפעול: שם התוכנה, יצרן, גרסה ומסך הגדרות תקשורת קיים.
- [ ] במחשב Vuniq: צילום מנהל המשימות עם Vuniq, NILIT וכל שרת/תוכנת תקשורת רלוונטיים. לרשום PID, חשבון משתמש ומספר מופעים.
- [ ] מתוך תהליך, אם האפשרות קיימת, Open file location ו־Properties → Details. זה מזהה את הקובץ הפעיל, ולא רק קיצור דרך או עותק גיבוי.

המשמעות: להפריד בין יצרן המחשב, התוכנה המציגה על ה־HMI והתוכנה שמטפלת בתקשורת. הם אינם בהכרח אותו ספק. מנהל המשימות לבדו אינו מוכיח מי מחזיק פורט טורי; אם אין אבחון קיים לזה, לסמן שהבעלות על הפורט טרם אומתה.

## 2. החיבור הפעיל ב־Vuniq — עדיפות גבוהה

בתיעוד הישן של Vuniq 5 התפריט נקרא Settings → Data Sources. השמות והמיקום עשויים להשתנות בגרסה שבשטח; להשתמש בחלון ההגדרות של הפרויקט שכבר רץ. אין לפתוח פרויקט אחר לצורך הבדיקה.

- [ ] צילום רשימת כל הפורטים, כולל מספר לוגי, Active, סוג Local/Remote/OPC ודרייבר.
- [ ] צילום מפורט של הפורט שמשרת את האקסטרודר שנבחר.
- [ ] אם זה חיבור טורי: COM, Baud, Data bits, Parity, Stop bits ו־Flow control/Handshake.
- [ ] אם קיימות הגדרות 3964R: לצלם בחירת 3964/3964R או BCC, Priority, זמני המתנה ומספר ניסיונות. אם אינן מוצגות, לרשום „לא מוצג”; לא להוסיף ערכים משוערים.
- [ ] אם זה OPC: שם השרת, כתובת/מחשב השרת אם מוצגים, וקבוצות/שמות פריטים קיימים. אם זה Remote: מחשב המקור והפורט הלוגי המרוחק.
- [ ] לצאת מהחלון ללא החלת שינויים.

| פריט | ערך שנמצא |
|---|---|
| פורט לוגי ב־Vuniq | |
| סוג חיבור פעיל | |
| דרייבר / שרת OPC | |
| מספר COM ב־Windows | |
| Baud / Data / Parity / Stop | |
| Flow control / Handshake | |
| 3964R/BCC, אם מוצג | |
| Priority / Timeouts / Retries, אם מוצגים | |

בגיבוי GH שמסר המשתמש נמצאו COM1–COM8, דרייבר Barmag, 9600/8/Even/1; זו נקודת השוואה בלבד. בגיבוי MN נמצא OPC. אין להחיל את ההגדרות האלה על המחשב הפעיל בלי לבדוק מה הוא משתמש בו בפועל. פורט לוגי 1 ב־Vuniq אינו בהכרח COM1.

3964R כולל אישורים ובדיקת בלוק BCC; הוא אינו לבדו מילון המשמעות של נתוני המכונה. אם מוצגת Priority בשני הצדדים, לרשום אותה; בתיעוד Siemens שני השותפים מקבלים עדיפויות שונות. אלה פרטים לאיסוף, לא הוראות לשינוי. [תיעוד Siemens](https://docs.tia.siemens.cloud/r/simatic_s7_1200_manual_collection_enus_20/communication-processor-and-modbus-tcp/point-to-point-ptp-communication/configuring-3964-r-communication/configuring-the-3964-r-priority-and-protocol-parameters).

## 3. זיהוי חומרת ה־COM ב־Windows

- [ ] Device Manager → Ports (COM & LPT): צילום הרשימה.
- [ ] עבור הפורט הרלוונטי: יצרן/דגם, גרסת דרייבר ופרטי מיקום/מספר סידורי אם מוצגים.
- [ ] לרשום אם זה פורט מובנה, כרטיס מרובה יציאות, מתאם USB או פורט וירטואלי של רכיב רשת.
- [ ] לקשר את המספרים למחברים הפיזיים באמצעות סימון קיים בלבד. אם אין התאמה ברורה, להשאיר „לא זוהה”; לא לנתק יציאות כדי לגלות.

הגדרות ברירת המחדל במנהל ההתקנים אינן הוכחה להגדרות שבהן היישום משתמש: תוכנה יכולה לקבוע את פרמטרי הפורט בזמן הריצה. [דוגמת Microsoft להגדרת פורט ביישום](https://learn.microsoft.com/en-us/windows/win32/devio/configuring-a-communications-resource).

## 4. צפייה בתקינות ובתנועה — 2–3 דקות

בתיעוד הישן של Vuniq 5 מופיע Current State עבור פורט, ובו מצב תקשורת, פריטים/בלוקים, קצב עדכון וזמן תגובה. לצלם את השדות שהגרסה בשטח אכן מציגה.

- [ ] מצב הפורט לפני ההמתנה ואחריה, ושגיאה אחרונה אם קיימת.
- [ ] מוני שידור/קליטה/שגיאות/ניסיונות חוזרים, אם מוצגים. לצלם בתחילה ובסוף כדי לדעת אם הם מתקדמים.
- [ ] אם יש Serial Trace מובנה, תצוגת אבחון קיימת או רישום זמין: לשמור קטע קצר של TX ו־RX עם השעה והבייטים המלאים. להעדיף טקסט/Hex על צילום חלקי; אם אין יצוא, לצלם או להקליט את התצוגה.
- [ ] לסמן את הפורט, הקו והמצב התפעולי של המכונה באותו זמן.

מסגרת רגילה של 3964R כוללת פתיחה, אישור, תוכן, סיום ובדיקת BCC; לכן צריך את שני כיווני התנועה, לא רק את ההודעה שהתקבלה. [תיעוד השידור של Siemens](https://docs.tia.siemens.cloud/r/en-us/v21/configuration-for-point-to-point-links-s7-300-s7-400/basic-information-s7-300-s7-400/data-transmission-with-3964-r-s7-300-s7-400/sending-data-with-3964-r-s7-300-s7-400).

להשתמש בתצוגת האבחון הקיימת בלבד. אם נדרשת התקנת כלי, החלפת דרייבר, הפעלה מחדש או חיבור פיזי נוסף — לרשום שאין לכידה זמינה בביקור הזה. אין לפתוח PuTTY/Terminal/סקריפט על אותו COM: ב־Windows הפורט נפתח בדרך כלל בגישה בלעדית, ופתיחה מתחרה אינה דרך להאזין לחיבור הפעיל. [תיעוד Microsoft](https://learn.microsoft.com/en-us/windows/win32/devio/communications-resource-handles).

## 5. בדיקת ראש אחד מהמקור עד המסך

לבחור ראש מזוהה אחד. להעדיף כתובות שכבר מוצגות/נקראות במערכת. אם משתמשים ב־Data Monitor של Vuniq, לצפות ב־Current Value בלבד; לא להשתמש בשדה שינוי ערך או בפקודת כתיבה.

בתצורת GH המאומתת, דוגמה לראש1 בפורט1 היא:

| מידע | כתובת לדוגמה |
|---|---|
| מצב ליפוף גולמי | `1;1;DW81.0` |
| שעת ניקיון | `1;1;S10` |
| יום ניקיון | `1;1;S11` |
| מצב מחושב של NILIT | `99;1;N11` |
| משך מצב מחושב | `99;1;N111` |

אלה דוגמאות למיפוי GH בלבד. להשתמש בהן רק אם הפורט והראש אכן תואמים לתצורה הפעילה. ב־MN המקור הוא שתי כתובות מהירות OPC, ויש להביא את השמות המדויקים מתוך התצורה הפעילה.

- [ ] צילום המצב בצד ה־HMI של המכונה ובמסך Vuniq עבור אותו ראש.
- [ ] רישום הכתובת, הערך הגולמי, המצב המחושב והזמן המוצג, עם שעה.
- [ ] אם במהלך עבודה רגילה מתרחש שינוי: לתעד את שעת השינוי במכונה, בנתון הגולמי ובמסך. אין ליזום עצירה או ניקיון לצורך הביקור.
- [ ] אם אין שינוי טבעי, לרשום זאת. ערך קבוע אינו מוכיח תקיעה, ומונה זמן מתקדם לבדו אינו מוכיח שנתוני המכונה טריים.

## 6. הפעלה אוטומטית ותקלות קודמות

- [ ] לבדוק קיצורים בתיקיות Startup של המשתמש ושל כלל המשתמשים: יעד מלא, ארגומנטים ו־Start in.
- [ ] לבדוק רשומות Startup הקיימות ב־Windows; ב־Win10 בדרך כלל במנהל המשימות, וב־Win7 אפשר לצפות בלשונית Startup של msconfig. לא לשנות סימונים.
- [ ] Task Scheduler: משימות Vuniq/NILIT/תקשורת; לצלם Trigger, Action, חשבון הפעלה, תנאי הפעלה, תוצאה אחרונה, ושאלה אם נדרשת כניסת משתמש. לא ללחוץ Run או End לצורך הבדיקה.
- [ ] אם נמצא שירות תקשורת/OPC: לצלם שם שירות, מצב, סוג הפעלה, נתיב והגדרות Recovery.
- [ ] Event Viewer / יומן Vuniq: לתעד אירועי קריסה, התחלה, timeout או ניתוק רלוונטיים עם שעה, שם היישום וטקסט מלא.
- [ ] לברר עם המפעיל מה הוא פותח ידנית לאחר הדלקת המחשב ומהו סדר ההפעלה בפועל. זו עדות מפעיל, בנפרד מהתצורה שנצפתה.

אין צורך לסגור NILIT, להפעיל מחדש Vuniq, לנתק כבל או לאתחל מחשב בביקור התיעוד. בדיקת התאוששות לאחר תקלה תהיה בדיקה נפרדת במועד מתאים למערכת.

## 7. מה להביא בחזרה

עדיפות ראשונה: צילומי תצורת הפורט הפעיל; רשימת תהליכים ונתיבי EXE; דגם ה־HMI והתוכנה שבו; תצפית ראש אחד; רישום TX/RX אם הוא זמין.

קבצים מהתיקיות הפעילות שזוהו, עם תאריך ושם מחשב:

- [ ] `vuapp.ini`, `settings.sxml`, `barmag.ini`, המסכים הרלוונטיים ו־`RTVar.sxml` אם קיים.
- [ ] `Vuniq.exe`, ה־DLL של הדרייבר הפעיל, `NILIT.exe`, וקוד VB המצורף אם קיים — להעתקה וניתוח בלבד.
- [ ] קיצור/קובץ הפעלה ומשימה מתוזמנת מיוצאת כ־XML, אם נמצאה.
- [ ] קטעי לוג רלוונטיים או יצוא דרך הממשק הקיים. העתקת מסד נתונים בזמן כתיבה אינה מבטיחה צילום עקבי; לצורך הביקור הראשוני מספיקים אירועים מיוצאים וצילומים.
- [ ] אם המקור OPC: שם המוצר והגרסה, נתיב ההתקנה, ושמירת תצורת השרת באמצעות אפשרות גיבוי קיימת שאינה מפעילה או משנה את התקשורת.

גיבויי GH/MN הקודמים משמשים להשוואה. קובץ שנלקח ממיקום אחר מהיישום הפעיל אינו מחליף את התיעוד של המערכת שרצה עכשיו.

## גבולות הראיות

תפריטי Vuniq מסתמכים על התיעוד המקומי ההיסטורי של Vuniq 5, עמודים 21–25; לא אומתה כאן זמינותם בגרסה שרצה בשטח. מסמך Siemens מסביר את הפרוטוקול ואינו מזהה את דגם הציוד אצל המשתמש. תצפית תקינה אחת אינה מוכיחה התאוששות לאחר ניתוק או אתחול. כדי לבנות סימולטור שימושי נצטרך בהמשך הקלטות של מספר מצבים טבעיים ומיפוי הנתונים, בנוסף לזיהוי 3964R.
